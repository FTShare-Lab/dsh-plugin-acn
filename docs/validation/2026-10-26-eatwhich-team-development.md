本次使用已安装 ACN 的本机 DSH，在现有 EatWhich 小程序上开发“历史计划再做一次”。数据层、界面、独立验收由三个 DSH 身份完成，连接同一个本地 Router / Maintainer。实现、测试和工作轨迹来自实际开发，没有预先植入正确答案或冲突 Claim。

实际结论：知识形成、跨成员发现、Policy 内化、Dream 查证和私有 Memory 能参与开发；项目新功能完成，独立审查发现的持久化 P1 已修复。首次启用 Router 模型重排时，两条自然争议均因候选集合波动未能自动采纳。随后按用户要求关闭 Router 模型重排，两条原争议均在首轮自动采纳，裁决送达三个成员，界面 Claim 原地收窄后回传团队；两组配置的结果分别保留如下。

## 实际开发的功能

历史卡片增加“再做一次”入口，预览当前还能使用的菜，以及已删除、隐藏或数据无效的菜。用户确认后，使用当前菜谱的名称、单位、耗时等信息替换“这次想吃”。全部不可用时保留原选择；不会复活隐藏菜、修改历史计划或自动创建新计划。

确认使用一次性预览 token，并检查历史计划、相关菜谱、当前选择是否在预览后变化。过期、取消、重复确认和数据变化均有处理。组件在切换历史卡片、筛选、刷新和卸载时释放预览，保留用户当前编辑的日期、时间和备注。

### 开发中自然形成的争议

独立验收实际发现：选择存储损坏时，`previewPlanReuse` 调用的既有 `getSelection` 会自愈写回空数组，并增加 revision。因此“预览零写入”应限定正常数据，不能作为无条件事实。该低频异常没有作为新 P1 扩大业务修复范围，但需要修正知识的适用条件。

执行者另用当前真实 storage 模块独立复现：正常数据预览的写入数和 revision 变化均为 0；将选择存储替换为损坏对象后预览，冲刷产生 1 次自愈写入、revision 增加 1，最终存储为空数组。该复现同样仅限 Node wx mock。

数据层形成 `dispute_5e255280`，比较自己已经补充例外的 `claim_192a1c72` 与界面的无条件表述 `claim_2e0afaeb`。验收成员随后形成 `dispute_583eb001`，比较主契约与独立复现 `claim_8c8e81fa`；后一条在分析时主契约已经更新，因此可能属于旧版本误读，而非仍然成立的矛盾。两条均由真实 Recap/Finalize 产出，没有脚本代填 Dispute。

Maintainer 实际调用 `deepseek-v4-flash-api` 的提案与独立验证。前两轮采纳检查报告 source Claim 或 Router 候选变化，触发既有 5 分钟、15 分钟退避；approved 不等于 adopted。开发会话和形成任务全部结束后，03:25:26（本地时间）冻结并记录团队的 29 份 Claim SHA-256，03:40 再次核对仍全部相同。

第三轮结果仍未采纳：

| 自然争议 | 模型提案 / 独立验证 | 最终服务状态 |
| --- | --- | --- |
| `dispute_5e255280` | `conflict_resolved`，置信度 0.90；独立验证 approve，建议给界面 Claim 补上合法 selection 前提 | `open`；Analysis `approved`，第三次 `Router candidate Claims` 变化，自动处理停止，等待人工；无 Resolution |
| `dispute_583eb001` | `coexist`，置信度 0.95；独立验证 approve，当前两条正文已经兼容 | `open`；同样因第三次候选变化停止；无 Resolution |

这不是 DSH 插件消息丢失。直接对 Router 重放完全相同的仲裁查询，两轮分别合并两个 scope 的 top-k 结果，候选 ID 并集分别为 12 和 14 条，集合不同；29 份底层 Claim 全程没有变化。变化来自模型重排后 top-k 选择的波动，并非仅顺序变化。比如第二轮包含 `claim_7aba82ff`、`claim_8474d234`、`claim_af321ba9`，第一轮没有；第一轮的 `claim_82552c59` 又不在第二轮。

源码对应关系是：参考 ACN 的 `src/router/service.rs` 在模型重排后截取 top-k；`src/maintainer/arbitration/context.rs` 把返回候选集合计入语义指纹；`src/maintainer/arbitration/service.rs` 在采纳前重新调用 Router 构建上下文，集合变化就退避并重新分析。候选已按 ID 排序，因此给列表排序不能修复这次问题。稳定知识下重复检索仍会得到不同的证据集合，使自动仲裁无法收敛。

首次验收没有手动采纳、关闭模型重排、扩大 top-k、缩短退避，或放松指纹检查来制造成功。三个 DSH 成员随后实际执行 `/inbox` 均为拉取 0、确认 0、待内化 0，与尚无 Resolution 一致。此前两项 Policy 的成功传播仍成立，但不能替代自然争议的自动裁决及传播验收。参考服务保留原代码和失败现场；用户随后明确要求暂不修改该联动问题，先使用没有 LLM 的 Router，复验记录见下一节。

最后在修复后的知识交接会话再做只读核查：实际只调用一次 `consult_router`，成功读到两条 `open` Dispute、空的 `resolved_dispute_ids` 及有分歧的 Claim 正文。模型明确指出正常 selection 才能断言零写入、相关争议尚未解决，并说明工具没有仲裁内部阶段，无法判断具体处理进度。没有把候选提案或自己的判断说成已采纳裁决，也没有改写知识来掩盖未收敛状态。

## 独立审查发现的 P1

初版 `confirmPlanReuse` 调用已有延迟 `setSelection` 后立即返回成功。持续拒绝 `mydishes:cart` 写入时，实际复现得到：返回 `ok=true/applied=true`，内存是复用后的菜单，重启却恢复旧菜单。验收成员最初的测试还把“先成功、稍后重试”当成正确行为。

外部审查使用配置默认的 `gpt-6-astra`，直接只读执行，禁止嵌套审查、子代理、运行测试及写文件。旧 CLI `0.145.0` 返回要求升级的 HTTP 400，未计为完成；改用本机已有 `0.164.0-alpha.11.1` 后得到上述 P1。项目实现与 ACN 模型调用仍使用 `deepseek-v4-flash-api`。

## 使用中暴露的可用性限制

两个成员都曾把 `claim read` 返回的 `revision` 直接当作 update 入参；实际入参是 `expected_revision`。严格校验正确拒绝了错误调用，但通用 validation 消息没有指出具体字段，成员还尝试了不存在的 `help` 动作。执行者查阅实际 schema 后提示字段名，两者才成功用 CAS 更新自己的知识。这不是无干预的自动恢复，应计为工具反馈可改进之处。

还有一处语义变强：验收成员原先把“导入完全相同快照后旧预览仍能确认”列为需负责人决定的边界；形成的 `claim_3cf52fe2` 将重置 token 表述成所有整体恢复路径“都必须”执行，新会话又称其为已知漏洞。代码现象有 mock 复现，但“内容相同也必须失效”并非本轮已确定的产品要求。这一项没有当作 P1 修复；事实、建议和待决策规则仍需人工区分。

长工具轨迹也影响自动 Memory review：虽然验收配置设为每两轮复核，两个已完成两轮的会话窗口均达到 32,000 字符，保留内容只剩工具与助手条目，没有用户条目，因而未创建 review 任务。正常 Memory 工具写入和冻结快照不受这一条件影响；不能用它们的通过替代自动 review 验收。

随后数据层会话增加一个简短收尾回合，第 4 轮完成后自动 review `e57fd104-6cbe-4295-8134-35dd5c269beb` 成功，`changed=true/skipped=false`，更新了工具使用经验、测试入口和验证偏好。这证明 review 管线可运行，同时保留上述长轨迹触发条件的限制。
